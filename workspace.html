Run with Docker

cp .env.example .env
docker compose up --build
# web :8080  api :8000  qdrant :6333  grafana :3000

Call the API

curl -X POST localhost:8000/api/v1/detect \
 -H "x-api-key: change-me-1" \
 -H "content-type: application/json" \
 -d '{"channel":"P-1","window":[[0.1,0],[0.2,0]],"observed":0.9}'

Train on NASA data

python -m src.train --chan P-1 --epochs 5
echo WEIGHTS_PATH=weights/P-1.pt >> .env

FAQ

Is the detection on this page the real model?

No. The browser uses an EWMA baseline. The PyTorch model runs in the Docker backend after you train it.

Where do my API keys go?

Vercel environment variables for the hosted site, or .env for Docker. Never commit them.

Why human approval?

Throttling or isolating spacecraft subsystems is irreversible enough that a person must confirm it.

Security, Docker & limits

Security

  • API-key auth, token-bucket rate limit
  • CORS isolation, input validation (pydantic)
  • Payload dedupe (idempotency)
  • Secrets via env / Docker secrets; never in repo
  • HITL for throttle / isolation actions

Reliability & Docker

  • 200 ms budget then Z-score fallback
  • Multi-stage Dockerfile, non-root user
  • Compose: API + Qdrant + Grafana + nginx

Limitations

The website demo is simulated. The Python model ships untrained: you must train on NASA SMAP/MSL data. Thresholds vary per channel, LLM hypotheses must be verified, in-memory rate limiting suits one instance, seed incident notes are illustrative, not official NASA records, and this is not flight-qualified software.
